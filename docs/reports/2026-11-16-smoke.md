# 2026-11-16 本机冒烟测试

机器为 4 × NVIDIA H100 80GB HBM3，卡间 NVLink。隔离环境安装 SGLang 0.5.23、Transformers 5.19.0、PyTorch 2.14.1；模型为计划中的本地目录。测试服务使用 TP=4、BF16 权重、BF16 KV、262144 窗口和最多 4 个活跃请求。SGLang 启动日志确认权重加载完毕、KV cache 为 `torch.bfloat16`；首次启动经历内核编译。

- OpenAI Chat Completions：请求回复 hello，实际回复 `hello`。
- Anthropic Messages：工具选择返回 `calculator` 与 `{"expression":"2+3"}`；将工具结果 `5` 送回后，回复 `2 + 3 = 5`。流式请求观察到 message start、content block、message delta 和 message stop 事件。
- 长输入：使用 tokenizer 构造重复文本并提问，服务报告 `prompt_tokens=261020`、`completion_tokens=3`，回复 `42`。另一次边界请求的输入为 262118 tokens、请求预留 26 个输出 tokens，总预算恰为 262144；实际输出 3 tokens，回复 `42`。重复输入不能证明长上下文代码任务质量。
- 启动测试使用模型配置默认 recurrent state 精度。随后启动配置增加显式 `--mamba-ssm-dtype float32`；1M 测试使用此参数，切回 256K 后健康检查和 hello 请求也通过。
- 单元测试：`python3 -m unittest discover -s tests -q`，4 项通过，包含本地模拟流式服务的并发测试。

## 并发性能冒烟

执行 `python3 -m petitcoding.benchmark --requests 16 --concurrency 1 2 4 --output-tokens 64 --warmup 1`。相同短 prompt、相同服务实例、带前缀缓存，thinking 开启；输出 token 由后端 usage 报告，包括 thinking。该轮未并行发起其他推理请求；结果仅用于确认工具工作，不适合作为容量承诺。

| 并发 | 成功/请求 | 输出 tokens/s | TTFT p50 | 延迟 p50 |
| --- | --- | --- | --- | --- |
| 1 | 16/16 | 129.5 | 51 ms | 494 ms |
| 2 | 16/16 | 239.3 | 95 ms | 546 ms |
| 4 | 16/16 | 457.6 | 100 ms | 558 ms |

原始运行数据保存在本机临时目录 `/tmp/petitcoding-benchmark-isolated/`，不会提交仓库。16 个样本不适合判断尾延迟；正式测试需隔离其他请求、分别测冷/热缓存、长上下文和更多样本。

## vLLM 冒烟测试

另用隔离环境启动 vLLM 0.33.0、TP=4、BF16 权重与 KV、262144 窗口。短请求回复 `hello`；同一边界请求报告输入 262118 tokens、预留 26 tokens，实际返回 `42`。Anthropic Messages 返回 `calculator` 工具调用与 `2+3` 参数，回传结果后模型答出 `5`。未在 VS Code 中验证。

相同短 prompt、预热 1 次、每档 16 次、输出上限 64、thinking 开启：

| 并发 | 成功/请求 | 输出 tokens/s | TTFT p50 | 延迟 p50 |
| --- | --- | --- | --- | --- |
| 1 | 16/16 | 121.3 | 71 ms | 527 ms |
| 2 | 16/16 | 213.9 | 89 ms | 594 ms |
| 4 | 16/16 | 422.7 | 134 ms | 601 ms |

原始数据在 `/tmp/petitcoding-vllm-benchmark-final/`。两次运行的硬件和输入相同，但运行时依赖、缓存和调度实现不同；各档仅 16 个请求，不应据此做全面的后端性能排名。benchmark 同时识别 SGLang 的 `reasoning_content` 和 vLLM 的 `reasoning` 流事件。

## SGLang 1M 容量冒烟

使用 `configs/sglang-1m.toml`，TP=4、BF16 权重及 KV、FP32 recurrent state、单并发，YaRN factor=4。服务实际报告 `prompt_tokens=999740`、`completion_tokens=3`，成功返回 `42`。输入主体为重复文本，答案在文本中多次出现；这验证接近 1M 的单请求容量和基本输出，不能证明远距离检索、代码质量、多并发容量或 1M 窗口精确边界。模型 README 提醒静态 YaRN 可能影响短输入质量，默认配置仍使用原生 256K。
